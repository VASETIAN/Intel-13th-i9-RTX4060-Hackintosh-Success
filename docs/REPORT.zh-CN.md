# Intel 13代 i9 与 RTX 4060 黑苹果安装及适配报告

> 历史记录：本文保留 Sequoia 15.7.9 首次安装阶段。2026-11-01 当前系统已为 Tahoe 26.7.1，机主确认恢复开机，当前无 cpus=1，NVIDIA 为 2.6.2。后续、20 逻辑 CPU 原机证据和启动修复见 [macOS 26 记录](TAHOE26.zh-CN.md)与[当前状态表](STATUS.zh-CN.md)。下文的“最终”均指当时 Sequoia 阶段。

## 1 项目目标与完成结果

项目开始时，电脑运行 Windows 11，机主希望保留原系统及数据，在同一块内置 SSD 上增加 macOS，主要准备工作由项目工具完成。由于没有可用 U 盘，最终采用独立内盘引导区与 macOS 目标区的路线。安装过程中没有把整块 SSD 当作可抹除对象，也没有通过覆盖 Windows EFI 来替换原系统启动程序。

本报告的终点是：macOS Sequoia 15.7.9（24G830）已安装，OpenCore 可以启动 Macintosh HD，本地账户可以登录，Wi-Fi 正常，安装第三方 NVIDIA 2.5.4 驱动后机主反馈系统恢复正常日常使用。后来的容量扩展不属于本报告。

这个结果有明确限制：最终 macOS 配置仍含 `cpus=1`；没有完成全核性能、全部外设、长期负载或独立 Metal 基准验收；Apple ID 状态异常和 AirDrop 不可用仍有记录。这里的“可用”是对已完成安装与实际桌面使用的描述，不代表所有苹果生态功能都兼容。

## 2 硬件配置与适配前提

| 部件 | 本机实际配置 | 对适配的影响 |

| CPU | Intel Core i9-13900H，13 代 Raptor Lake H，6P + 8E，20 线程 | 不是苹果原生采用的移动平台，需要 CPU 兼容参数；多处理器启动成为主要障碍 |
| 独显 | RTX 4060 Laptop，`10DE:28E0` | 采用第三方 NullMoth 路线，不是苹果原生 NVIDIA 驱动 |
| 核显 | Iris Xe，`8086:A7A0` | 没有获得该核显加速的验证，不能用旧 Intel 核显模板直接推断兼容性 |
| 主板和固件 | Lenovo 21J8，LNVNB161216，BIOS LRCN52WW | ACPI 方法、设备路径和定向修补按这份固件核对；没有刷 BIOS |
| 内存 | 16 GB | 安装和设置问题曾做内存限制对照，但最终没有保留该临时限制 |
| SSD | Samsung MZVL21T0HCLR-00BL2，约 1 TB，固件 CL1QGXA7 | 使用 GPT/UEFI，Windows 和 APFS 位于同一物理 SSD |

## 3 采用的技术和工具

### 3.1 OpenCore 与原生 macOS 启动

固件从独立引导区加载 OpenCore，再由 OpenCore 处理 Apple 启动器、ACPI 和内核扩展注入，进入恢复环境或已安装系统。系统安装到 APFS 容器，包含 System、Data、Preboot、Recovery、Update、VM 等角色卷。

项目日志显示使用 DBG109，即 1.0.9 系列构建标识，配套本地 `ocvalidate` 1.0.9 完成静态检查。静态检查只能说明配置结构，不证明机器已经启动成功。本次公开整理时，官方 1.0.9 release 网页和 API 未提供可确认的下载结果，所以仓库记录实际构建标识与配置，不把猜测的下载地址当作来源。

### 3.2 CPU 和内存映射兼容

配置使用 CPU 身份兼容数据、`ProvideCurrentCpuInfo` 等设置，并最终保留 `cpus=1`。关闭了本机早期触发问题的 `DevirtualiseMmio` 路径。可选的 CpuTopologyRebuild、配套 force-HT 补丁和 `ctrsmt=full` 在建立稳定启动基线时被撤下。

`cpus=1` 限制的是本轮 macOS 内核使用的逻辑 CPU 数，不是把物理 CPU 改成单核，也没有修改 Windows 的 CPU 数量。它帮助本机越过早期启动障碍，但显著限制性能，不能在成功报告中省略。

### 3.3 ACPI 和驱动

最终配置使用十个 SSDT，包括 EC、GPI0、PLUG-ALT、RTC/AWAC、USBX、XOSI 和本项目定制的 EC RTCM overlay。基础扩展包括 Lilu、VirtualSMC、RestrictEvents、WhateverGreen、AMFIPass；网络使用 AirportItlwm，输入使用 VoodooPS2/VoodooI2C 等组合。完整版本见[依赖记录](DEPENDENCIES.zh-CN.md)。

显卡采用 1401 Mac 工具在已经安装的 macOS 中部署 NullMoth NVIDIA 2.5.4。系统驱动需要安装到 macOS 的扩展目录、准备相应缓存并重启；单纯把安装包下载到 Windows 或放入 EFI，不等于已经具备桌面加速。

### 3.4 诊断与保护

Windows 侧使用 PowerShell、Python、文件哈希和分区身份核对；macOS 侧保留安装日志、原生线程快照、账户检查结果。统一日志使用 Mandiant 的离线工具解析，ACPI 研究使用与错误日志年代一致的 ACPICA 20160930 用户态解释器。

QEMU 隔离副本用于验证加载器、脚本和部分 ACPI 行为，不连接原机物理盘、不代替原机验证。配置修改前保留快照，修改后核对实际文件和 OpenCore 日志；临时维护参数和测试项采用独立恢复逻辑，避免把诊断配置长期留在日常引导中。

## 4 实施过程

### 4.1 识别硬件并研究可行性

先读取整机、BIOS、CPU、GPU、无线、磁盘和显示路由，再比较 OpenCore 及相关驱动作者的资料。没有找到与整机、固件、CPU、GPU 和屏幕路由全部一致的可直接复用模板。相近 CPU 或显卡的其他机器，只作为调查线索，没有把它们的整套 EFI 当成本机成功证明。

### 4.2 准备无 U 盘引导和双系统保护

在机主批准的 D 盘空间范围内准备独立约 2 GiB 引导区及 macOS 目标空间。扩容前最终原 APFS 容器为 48,269,430,784 字节，约 44.95 GiB；早期卷名包含容量标签，不能把标签当成最终实际容量。

OpenCore、Apple 恢复镜像及校验文件放在独立区域。Windows 原 EFI、C 盘、已有文件及默认启动路径作为保护对象。进入 macOS 使用固件启动菜单选择 OpenCore；重启回到 Windows 有时只是固件默认行为，不能单凭这一现象断言 macOS 崩溃。

### 4.3 越过启动障碍并进入安装器

先修复恢复项被隐藏和倒计时误选 Windows 的菜单问题，再处理内存映射页错误、ACPI 补丁范围和 CPU 启动基线。最终 `cpus=1` 的实际启动能进入恢复和安装界面；两 CPU 对照重新停在早期阶段，因此恢复一 CPU 基线，没有把“更多 CPU 一定更好”当作前提。

### 4.4 完成多阶段安装

安装界面曾长期显示“剩余不到一分钟”。离线读取 Update 卷的 `restore.log`，定位到系统文件解包子阶段最后记录为 39%，当时仍约有 21.8 GiB 空间。没有据此认定磁盘不足或必须重新安装。

后续实际日志显示安装发生了阶段变化，部署引擎到达 100%，记录 `ota-result=success`、`FINISHED-ENGINES(SUCCESS)`，已写入的 `SystemVersion.plist` 为 15.7.9/24G830。OSInstaller 随后明确请求重启，下一步转为从 OpenCore 启动 Macintosh HD，而不是反复回到最初恢复镜像。

### 4.5 处理首次设置并建立可登录账户

已安装系统进入国家或地区页，选择中国大陆并点击继续后持续转圈。诊断显示点击事件已收到；原生线程快照把等待定位到 CountryManager 保存语言区域时等待辅助服务回调。Wi-Fi 同时存在 80 秒扫描超时，但没有证明它就是地区页等待的唯一原因。

保留正常联网后，多项有限对照未使设置流程推进。经机主明确同意，最终在已安装系统的维护模式中使用原生 Directory Services 建立本地管理员；密码由机主在隐藏提示中输入。在验证原生密码认证、管理员成员、主目录和 Secure Token 后才写入首次设置完成标记，再恢复普通启动进入登录界面。

这一步绕过了卡住的首次设置流程，没有证明 Setup Assistant 自身的原始故障已经修复。公开说明见[账户恢复章节](ACCOUNT-RECOVERY.zh-CN.md)，不提供绑定本机身份和扇区位置的现用账户脚本。

### 4.6 安装 NVIDIA 系统驱动并改善桌面体验

首次登录桌面后，Wi-Fi 可用，但文字和窗口偏小、鼠标移动卡顿。只读检查发现 NVIDIA 系统驱动目录尚未部署，不能把 EFI 中存在相关配置或材料下载成功当成安装完成。

核验 1401 Mac 2.5.4 和驱动归档的作者发布摘要后，在 macOS 中执行 NVIDIA 驱动安装、缓存准备和重启。扩容前备份记录已经能读取 NVRM、NVAccel、NVRMFB、NVRMAGDC 四个 2.5.4 扩展；机主随后明确反馈驱动已装好、使用正常。

高分辨率导致的文字过小按显示缩放处理，建议检查类似 1600 × 1000 的 HiDPI 逻辑模式，而不是仅因窗口尺寸就更换 SMBIOS。没有保存足够的运行时显示模式来宣称特定 HiDPI 模式已经单独验收。

## 5 主要故障及解决情况

### 5.1 OpenCore 只显示 Windows 并自动返回 Windows

**现象：** 菜单仅见 Windows，等待后自动进入 Windows。

**证据：** OpenCore 记录 `aux hidden`，配置 `HideAuxiliary=true`、`Timeout=5`，恢复镜像及 chunklist 实际存在。

**处理：** 将 `HideAuxiliary` 改为 `false`，使辅助恢复项显示；将 `Timeout` 改为 `0`，使安装诊断菜单等待手动选择。只调整菜单字段，并恢复 Windows Boot Manager 的默认优先级。

**结果：** 后续可以选择 macOS 恢复环境。该修改处理的是菜单可见性和默认项，不涉及系统驱动或系统安装是否成功。

### 5.2 早期 type 14 页错误与 ACPI 枚举后停顿

**现象：** 内核早期发生页错误，随后另一配置停在 ACPI 表列表附近。

**处理：** `DevirtualiseMmio=False` 后，实机越过原来的页错误。其后撤回可选 CPU 拓扑优化及配套参数，保留基础 CPU 兼容设置；将 GPIO 重命名限制到 DSDT 和一次匹配，避免误改其他 SSDT 中 TPM 与 NVIDIA 平台设备的 `_STA`。

**进一步结果：** 调整后的基线仍需单 CPU 诊断，加入 `cpus=1` 后进入安装界面；`cpus=2` 又出现早期停顿，故撤回。CPU 基础初始化与多处理器兼容性仍未被完整解决。GPIO 范围错误确实修正，但没有通过单独对照证明它就是原始卡点的唯一原因。

### 5.3 修改配置后旧启动参数仍出现

**现象：** 文件里已移除的参数仍能在实际启动日志中看到。

**处理：** 区分文件配置和固件里已有的 `boot-args`，定点更新本项目需要的启动参数，随后检查 OpenCore 实际传给 Apple 启动器的内容。没有用整机 Reset NVRAM 代替这一步，避免同时丢失其他固件设置。

**经验：** `ocvalidate` 通过和文件哈希正确，不能替代“本次启动确实使用了候选参数”的证据。

### 5.4 安装剩余时间不动和解包 39%

**现象：** 苹果标志下显示不到一分钟，等待几十分钟甚至更久；日志最后为解包 39%。

**判断：** 百分比属于当时子阶段，不是整个安装的总体比例，也不是错误码。可用空间、CPU 限制、存储 I/O 和进程等待需要分开看，没有发现可直接证明单核必定在 39% 死锁的依据。

**处理与结果：** 提取目标 APFS 的安装日志，而不是继续只按屏幕字幕等待或重新抹盘。后续日志证实部署完成并主动阶段重启，正确选择已安装的 Macintosh HD，继续首次启动。

### 5.5 AppleHDA 路径 panic 与没有生效的隔离尝试

一次 panic 为 `element modified after free`，回溯触及音频输入 DSP 和 AppleHDA 初始化路径。这说明崩溃被发现时位于该路径，不足以证明 AppleHDA 或 AppleALC 就是更早的内存破坏者。

曾准备并部署 AppleHDA `Disable` 隔离，但实际 OpenCore 日志显示模块在当前 Boot KC 中使用 kernel stub，阻断返回 `Unsupported`。因此**不能把后续安装成功归功于音频阻断**。该临时方案被撤回，最终可用配置没有启用 AppleHDA Block。此前存储电源管理探针也没有被当作已经证实的修复长期保留。

### 5.6 首次设置国家地区页持续转圈

两次设置进程的日志均收到 Continue 点击；线程快照显示主线程仍处理事件，协作队列线程在 CountryManager 方法中等待。由此排除了“按钮根本没有收到输入”这一简单解释。

关闭 Wi-Fi 的诊断在实际对照前因保留联网需求撤回，不能说它试验成功或失败；无线扫描超时与国家设置回调等待也没有建立完整因果链。8 GiB 内存限制对照实际未改善并恢复。结束 Setup Assistant 的尝试触发临时会话退出和系统关机，未能执行后续重开命令，该方案撤回。

单 CPU 与 Swift 协作任务可能存在调度互锁风险，但本机没有成功完成相应进程环境参数对照，不能把这个假说写成已确认根因。最后采用获准的本地账户替代流程进入桌面，保留原始设置助手问题未完全解释这一事实。

### 5.7 单用户模式 ACPI RTCM 无限刷屏

错误包含 `No handler for Region [RTCM]`、`SystemCMOS`、`AE_NOT_EXIST`，调用链指向 EC0 的 `SNTM` 与 `_Q77`。原固件的 SNTM 读取 AWAC 小时、分钟字段，再写入 EC 时间字段；隐藏 AWAC 设备并不会自动消除 AML 中直接读字段的调用。

处理方式是仅在匹配的 DSDT 中将原 SNTM 定义改名为 XNTM，再加入 `SSDT-EC-RTCM`：Darwin 下的新 SNTM 直接返回，其他系统仍调用原 XNTM。该补丁按表长度、OEM 表标识和唯一匹配限制作用范围。

同版 ACPICA 离线测试复现了缺少 CMOS handler 的错误，修补后 Darwin 分支连续调用未再访问该字段，非 Darwin 分支保留原路径。后续维护账户流程实际能够继续，但没有据此宣称所有 EC 行为、睡眠或地区页故障都已修复。源码及限制见[补丁说明](../patches/README.md)。

### 5.8 维护脚本启动参数检查误停

脚本曾显示 `STOP: Unexpected maintenance boot arguments`，此时尚未开始创建账户。旧校验把整串启动参数逐字比较，不能容忍无意义尾部空白。OpenCore 的 custom slide 处理源码和本次引导日志，支持“移除内部参数后留下空白”的解释；当时未直接取得内核返回字符串的全部原始字节。

修订按参数词规范空白，再严格比较。不排序、不忽略未知参数，仍拒绝缺少 `-s`、CPU 限制变化或多出未知参数的情况。独立 Sequoia 副本进行了 22 个接受与拒绝测试。公开仓库附只处理字符串的独立示例，不附账户写入程序。

### 5.9 密码确认失败后已有部分账户

原生认证返回 `-14090 / eDSAuthFailed`，程序主动停止并保留部分账户。照片不能证明一定是用户输错密码，也不能排除维护环境认证问题。回到 shell 提示符后输入密码会变成 shell 命令，不能继续上一流程。

只读核对发现账户、管理员成员和主目录已存在，因此后续不再创建或删除账户、不重设密码，改为仅验证已有账户。原生认证、Secure Token、管理员成员与主目录检查通过后才写首次设置完成标记。返回 Windows 后确认临时 `-s` 已移除，保留 `cpus=1` 与 ACPI 修补，随后机主成功图形登录。

### 5.10 桌面卡顿与窗口字体很小

第一次桌面检查时 `/Library/GPUBundles` 为空，NVIDIA 系统扩展未部署。这个事实比“机型伪装与屏幕不一致”的推测更能解释当时缺少 NVIDIA 显示加速的状态；单 CPU 也限制性能。

1401 Mac 与驱动完整归档按固定版本和哈希准备，在 macOS 原生安装后重启。扩容前证据确认四个 NVIDIA 2.5.4 kext，机主反馈正常。最终配置对 `IONDRVSupport` 使用 Exclude，以处理与 NVRMFB 的固件 framebuffer 竞争；不能把它与此前无效的 AppleHDA 阻断混为一谈。

高分辨率下优先调整显示缩放。没有为此重新生成机型身份，也没有以更换 SMBIOS 冒充已经修复 Apple ID。

## 6 扩容前最终配置与状态

最终 SMBIOS 为 MacBookPro16,1。CPU 身份兼容数据前四字节为 `55060A00`，掩码前四字节为 `FFFFFFFF`；保留 `ProvideCurrentCpuInfo=True`、`AppleXcpmCfgLock=True`、`DevirtualiseMmio=False` 和 `cpus=1`。这些是本机可用配置记录，不是对所有 13 代 Intel 平台的通用参数推荐。

最终未启用 CpuTopologyRebuild、itlwm 或 NootedGreen；使用 AirportItlwm Sequoia 2.4.0 alpha 分支。USB 仍采用 USBToolBox 与 UTBDefault 等临时组合，未形成完整逐端口验收结论。

NVIDIA 2.5.4 的系统扩展已落盘，实际安装后机主反馈日常使用正常。没有独立证明所有 Metal 接口、硬件视频编解码、外接显示、睡眠唤醒或长时间高负载稳定性。

Apple ID 第一次验证码后曾显示登录、手机能看到设备，但设置界面随后不一致；本地存在账户记录，不能断言账号完全没有保存或密码错误。未删除钥匙串、账号数据库或重新生成硬件身份来试运气。AirDrop 机主明确反馈不可用，不能用 Wi-Fi 正常代替这项验收。

## 7 后续重装应保留的参考

应保留可用 EFI 的私人副本、对应版本和哈希、独立 ACPI 修补源码、CPU 限制与配置差异、安装阶段选择规则，以及账户替代流程的校验条件。公开仓库只保存脱敏材料，不代替包含个人文件的系统备份。

重装时先按正常设置流程尝试。如果再次出现同一故障，应先确认版本、启动参数、实际等待位置和账户状态；不能直接照搬上次的磁盘号、分区 UUID、账户名或扇区读取命令。已经存在部分账户时，先检查并续验，避免重复创建。

更换 BIOS、系统版本、OpenCore 构建或驱动版本后，需要重新验证。尤其不能把当前单核可用配置描述为全核问题已经解决，也不能为追求新版本而一次替换全部组件后仍宣称复现了本报告。
